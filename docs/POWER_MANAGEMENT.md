## 1. 设计目标

### 1.1 核心目标

本项目包含多个 AI 应用和独立工具应用，涉及 AMOLED 显示、Wi-Fi 通信、语音采集与播放、动画渲染、TF 卡读写等功能。

如果各应用独立维护定时器、网络连接和外设资源，容易出现应用退出后仍然持续联网、动画继续运行、音频外设没有关闭等问题。

因此需要建立统一的电源管理体系，由系统统一协调应用生命周期、网络任务、显示状态、音频外设和 CPU 运行状态。

主要目标：

1. 降低设备空闲状态下的平均功耗。
2. 应用离开前台后，停止该应用所有非必要业务活动。
3. 显示屏在无操作时自动降低亮度或关闭。
4. 音频采集、播放结束后及时释放相关硬件资源。
5. Wi-Fi 按实际业务需要使用，避免无意义的定时轮询。
6. 根据当前运行场景动态调整 CPU 性能。
7. 为后续 Light Sleep、Deep Sleep 等低功耗模式预留扩展能力。
8. 建立统一的功耗监测与测试机制，最终通过实测优化。

### 1.2 第一版设计原则

| 原则    | 具体要求                   |
| ----- | ---------------------- |
| 前台独占  | 同一时间只运行一个业务应用          |
| 无后台服务 | 第一版所有应用均不提供后台业务运行      |
| 按需联网  | 进入应用后才启动该应用需要的网络请求     |
| 退出即释放 | 离开应用后停止定时任务、断开业务连接     |
| 状态可恢复 | 保存必要的业务数据和会话信息，不保留后台连接 |
| 统一调度  | 由系统服务统一管理显示、音频、网络和 CPU |
| 分级省电  | 优先关闭不需要的外设，再考虑系统级睡眠    |
| 数据驱动  | 以实际电流和续航测试结果作为优化依据     |

特别说明：第一版不追求复杂的后台任务保活、自动唤醒和多应用并行运行。优先保证交互可靠性和功耗管理简单可控。

| 16MB Flash     | 固件和配置存储                    | Flash 读写频率     |

| CO5300         | AMOLED 显示控制                | 面板休眠和唤醒        |
| CST9220        | 触摸控制                       | 触摸扫描及唤醒        |
| ES8311         | 音频 Codec                   | 音频工作状态、PA 控制   |
| ES7210         | 麦克风 ADC                    | 录音时启用，空闲时关闭    |
| QMI8658        | IMU                        | 采样频率、传感器休眠     |
| AXP2101        | 电源管理芯片                     | 电池状态、电源轨管理     |
| PCF85063       | RTC                        | 低功耗时间保持        |
| TF/MicroSD     | 本地音乐及文件                    | 避免持续读写         |

### 2.2 主要耗电模块

以下是基于硬件功能和典型工作场景的工程优先级判断，不代表已经测得的实际功耗排名。

| 模块     | 可能的耗电原因            | 优化优先级 |
| ------ | ------------------ | ----- |
| AMOLED | 高亮度、长时间亮屏、频繁刷新     | 最高    |
| Wi-Fi  | 长连接、频繁请求、网络重试      | 最高    |
| 音频     | 麦克风采集、Codec、功放持续工作 | 最高    |
| CPU    | 高频运行、动画解码、无效任务循环   | 高     |
| PSRAM  | 大量缓存、动画资源长期驻留      | 中     |
| TF 卡   | 连续读取、频繁文件访问        | 中     |
| IMU    | 高频采样、持续工作          | 中     |
| RTC    | 时间保持               | 低     |

优化顺序建议：

1. 屏幕自动关闭。
2. Wi-Fi 和业务连接按需运行。
3. 音频外设及时关闭。
4. 动画停止和 CPU 降频。
5. IMU、TF 等外设按需启用。
6. 最后再评估 Light Sleep 和 Deep Sleep。

## 3. 总体架构

建立独立的 Power Manager，由它统一协调其他系统服务。

### 3.1 系统模块

| 模块                   | 职责                   |
| -------------------- | -------------------- |
| Power Manager        | 电源策略、状态管理、低功耗协调      |
| App Manager          | 应用生命周期和前后台切换         |
| Display Manager      | 屏幕亮度、刷新、休眠、唤醒        |
| Audio Manager        | 麦克风、Codec、功放和 I2S 管理 |
| Network Manager      | Wi-Fi、网络连接、请求和重试     |
| Storage Manager      | TF 卡、文件和缓存资源         |
| Animation Manager    | 动画帧率、解码和暂停           |
| Device Monitor       | 电池、电源、内存和运行状态监测      |
| Notification Service | 系统提示，不承担后台业务轮询       |

### 3.2 模块关系

```
                 App Manager
                      |
              应用生命周期事件
                      |
                Power Manager
                      |
       +--------------+--------------+
       |              |              |
 Display Manager  Audio Manager  Network Manager
       |              |              |
   AMOLED/Touch   Codec/ADC/I2S     Wi-Fi
       |
 Animation Manager
       |
   LVGL / 动画资源

       Storage Manager
              |
          TF / FATFS

       Device Monitor
              |
       AXP2101 / Heap / CPU
```

所有业务应用不直接管理底层电源状态，而是通过统一系统服务申请资源。

## 4. 应用生命周期与电源管理

### 4.1 第一版统一规则

所有业务应用均采用前台独占运行模式。

应用状态：

| 状态         | 说明          |
| ---------- | ----------- |
| STOPPED    | 应用未运行       |
| FOREGROUND | 应用处于前台，正常运行 |
| EXITING    | 正在退出，释放资源   |

第一版不实现应用级后台运行状态。

### 4.2 应用切换流程

进入应用：

1. App Manager 创建或恢复应用实例。
2. 应用加载本地配置和缓存。
3. 根据需要申请显示、音频和网络资源。
4. 需要联网的应用立即触发一次数据刷新。
5. 启动该应用自己的前台定时任务。

离开应用：

1. 通知应用停止定时任务。
2. 取消可以安全取消的网络请求。
3. 断开 WebSocket、HTTP 长连接、SSH 等业务连接。
4. 停止音频采集和播放。
5. 停止动画解码和渲染。
6. 关闭不再使用的外设。
7. 释放临时缓存。
8. 保存必要的应用状态。
9. 通知 Power Manager 重新评估系统功耗状态。

退出时如果存在无法立即取消的请求，可以等待一个有限的清理时间；超时后进行安全清理，避免应用切换被无限阻塞。

### 4.3 各应用行为

| 应用                  | 前台行为          | 离开前台后的行为       |
| ------------------- | ------------- | -------------- |
| Muse                | AI 会话、语音交互、动画 | 结束会话，断开连接，关闭音频 |
| 大肥鱼                 | 模型对话、消息展示     | 停止请求，保存聊天记录    |
| 小智                  | 小智服务连接、语音交互   | 结束语音会话，断开连接    |
| Music Player        | TF 音乐播放       | 停止播放，释放音频资源    |
| Subscription Center | 查询账号额度        | 停止刷新，保留缓存      |
| ZCode Remote        | 连接和查看远程会话     | 断开连接，保存会话信息    |
| Weather             | 查询和展示天气       | 停止刷新，保留缓存      |
| Komari Monitor      | 查询服务器状态       | 停止监控连接和轮询      |
| File Manager        | 浏览和操作文件       | 结束操作，保存必要的浏览位置 |
| Settings            | 修改系统配置        | 保存配置，释放页面资源    |

**重要：第一版所有应用均不允许因为离开前台而继续维持业务连接。**

## 5. Network Manager 网络功耗管理

### 5.1 核心策略

采用：

**进入应用立即刷新 + 前台周期刷新 + 离开应用停止刷新。**

不允许应用在后台继续执行额度查询、天气查询、服务器监控等定时任务。

### 5.2 各应用刷新策略

以下是建议初始值，实际刷新周期应允许后续配置。

| 应用                  | 前台刷新间隔       | 进入前台     |
| ------------------- | ------------ | -------- |
| Subscription Center | 15～60 分钟，可配置 | 立即查询     |
| Weather             | 30～60 分钟     | 立即查询     |
| Komari Monitor      | 1～5 分钟，可配置   | 立即查询     |
| ZCode Remote        | 按需获取，不做后台轮询  | 用户手动恢复会话 |
| Muse                | 按会话需要请求      | 按需建立连接   |
| 大肥鱼                 | 按会话需要请求      | 按需建立连接   |
| 小智                  | 按语音会话需要请求    | 按需建立连接   |

### 5.3 数据缓存策略

进入应用时不应无条件等待网络返回。

建议采用：

1. 先展示本地缓存。
2. 后台立即发起网络刷新。
3. 请求成功后更新页面。
4. 请求失败时保留旧数据，并显示更新时间和错误状态。

缓存数据需要记录：

- 数据内容
- 更新时间
- 数据来源
- 是否过期
- 最近一次请求结果

缓存有效期与刷新周期是两个独立配置，不应混为一谈。

### 5.4 网络请求管理

Network Manager 统一管理：

- Wi-Fi 连接状态。
- HTTP 请求。
- WebSocket 连接。
- 请求超时。
- 网络重试。
- 请求取消。
- 连接复用。
- 请求并发控制。

优化规则：

1. 同一业务资源同一时间只允许一个刷新请求。
2. 应用离开时取消非必要请求。
3. 网络失败采用指数退避，避免连续重试。
4. 合并短时间内重复的查询请求。
5. 合理复用 HTTP Keep-Alive。
6. 不允许各应用自行建立无限重试循环。
7. 无业务需求时不主动保持 Wi-Fi 长连接。

### 5.5 Wi-Fi 电源策略

| 状态        | Wi-Fi 策略               |
| --------- | ---------------------- |
| 应用需要联网    | 连接并保持可用                |
| 应用内部暂时无请求 | 根据业务需要决定是否保持连接         |
| 应用退出      | 断开业务连接                 |
| 无其他网络需求   | 可关闭 Wi-Fi              |
| 系统空闲      | 根据是否需要远程唤醒决定是否断开 Wi-Fi |

第一版建议在没有任何前台网络需求时关闭 Wi-Fi。

Wi-Fi 重新连接可能产生额外耗电和等待时间，因此应通过实际测试比较持续连接与按需连接的总能耗。

## 6. Display Manager 显示功耗管理

AMOLED 是优先优化对象。

### 6.1 屏幕状态

定义四种显示状态：

| 状态          | 屏幕表现    | 动画       |
| ----------- | ------- | -------- |
| ACTIVE      | 正常亮度    | 正常运行     |
| DIMMED      | 降低亮度    | 降低帧率     |
| DISPLAY_OFF | 面板关闭或休眠 | 完全停止     |
| WAKEUP      | 恢复显示    | 重新加载当前状态 |

### 6.2 自动熄屏配置

建议提供以下选项：

- 15 秒
- 30 秒
- 1 分钟
- 2 分钟
- 5 分钟
- 永不熄屏

第一版默认建议 30 秒或 1 分钟，最终通过实际使用测试调整。

### 6.3 亮度管理

建议支持：

- 低亮度
- 中亮度
- 高亮度
- 自动调节（如果后续具备可靠的环境光数据来源）

默认采用中等亮度，避免不必要的高亮度显示。

### 6.4 熄屏实现要求

不能只将 LVGL 页面设置为黑色。

真正的熄屏需要：

1. 停止不必要的 LVGL 刷新和动画定时器。
2. 调用 CO5300 对应的面板休眠或关闭命令。
3. 按硬件设计关闭不需要的显示电源或背光相关电源域（仅在驱动和硬件支持时）。
4. 保留必要的触摸唤醒能力。
5. 避免熄屏后仍然频繁进行全屏刷新。

具体控制命令和电源轨操作必须以 Waveshare BSP 和面板驱动实现为准。

### 6.5 触摸唤醒

屏幕关闭后：

- 触摸事件用于唤醒屏幕。
- 第一次触摸只唤醒，不触发页面点击。
- 唤醒后恢复当前应用界面。
- 重置自动熄屏计时器。

如果触摸控制器无法在目标睡眠模式下独立唤醒，需要评估 GPIO 中断、控制器工作模式和系统睡眠配置。

## 7. Audio Manager 音频功耗管理

音频外设应采用按需启用原则。

### 7.1 音频状态

| 状态        | 麦克风      | Codec/播放 | 功放 |
| --------- | -------- | -------- | -- |
| IDLE      | 关闭       | 停止       | 关闭 |
| LISTENING | 开启       | 按需       | 关闭 |
| THINKING  | 关闭或按协议需要 | 通常停止     | 关闭 |
| SPEAKING  | 按需       | 开启       | 开启 |
| STOPPING  | 关闭       | 停止       | 关闭 |

### 7.2 资源释放

当语音交互结束：

1. 停止麦克风采集。
2. 停止 I2S DMA。
3. 停止 I2S 时钟。
4. 关闭 ES7210 采集路径。
5. 关闭 ES8311 不需要的工作路径。
6. 关闭功放。
7. 释放音频缓冲区。
8. 释放 Audio Manager 资源锁。

### 7.3 音频独占

Muse、大肥鱼、小智和 Music Player 共用 Audio Manager。

第一版采用独占策略：

- 同一时间只能有一个应用持有音频资源。
- 应用退出必须释放音频资源。
- 不支持跨应用后台音乐播放。
- 不支持多个 AI 助手同时监听。

Music Player 熄屏后是否继续播放属于单独的后台播放功能；第一版不实现，熄屏不等于允许应用离开前台后继续播放。

## 8. Animation Manager 动画功耗管理

角色动画不应该成为持续占用 CPU 和 PSRAM 的任务。

### 8.1 动画帧率建议

以下为第一版初始目标值，不是硬件实测最优值。

| 动画状态        | 建议帧率     |
| ----------- | -------- |
| Idle        | 2～4 FPS  |
| Listening   | 6～8 FPS  |
| Thinking    | 4～6 FPS  |
| Speaking    | 8～12 FPS |
| Happy       | 8～12 FPS |
| Sleep       | 1～2 FPS  |
| DISPLAY_OFF | 0 FPS    |

### 8.2 优化规则

1. 静止状态尽量使用单帧。
2. 只更新角色实际变化区域。
3. 避免无必要的全屏刷新。
4. 屏幕关闭后停止动画解码。
5. 离开应用后释放动画临时缓存。
6. 动画资源按需加载。
7. 避免多个动画任务同时运行。
8. 尽可能复用已加载资源。

### 8.3 动画资源管理

建议采用按需加载机制：

- 应用进入时加载当前角色资源。
- 切换角色时释放旧角色不再使用的缓存。
- 动画状态切换时优先复用已加载资源。
- 应用退出时释放可释放的 PSRAM 缓存。

## 9. CPU 与内存管理

### 9.1 CPU 频率管理

ESP32-S3 支持动态 CPU 频率管理，建议结合 ESP-IDF Power Management API 实现。

建议定义三种性能等级：

| 模式          | 使用场景              | 策略        |
| ----------- | ----------------- | --------- |
| PERFORMANCE | 语音处理、复杂 UI、动画密集任务 | 使用较高频率    |
| BALANCED    | 普通页面、网络请求         | 使用平衡频率    |
| LOW_POWER   | 页面空闲、轻量展示         | 降低 CPU 频率 |

实际频率由 ESP-IDF 配置、时钟源和电源管理驱动共同决定，不应在业务代码中随意修改 CPU 时钟。

注意：如果启用了 CPU 动态降频，需要评估 FreeRTOS Tick、外设时钟和音频实时性。

### 9.2 任务调度

优化要求：

- 避免使用无延时的 while 循环轮询。
- 使用事件通知和队列代替高频检查。
- 空闲任务应有充分运行机会。
- 定时任务只在前台应用活动期间创建。
- 应用退出时删除或停止相关任务。
- 控制任务栈大小，避免不必要的内存占用。

### 9.3 PSRAM 管理

建议对以下资源进行生命周期管理：

- 动画帧缓存
- 图片解码缓存
- 音频缓冲区
- HTTP 响应缓存
- 聊天消息临时数据
- 文件读取缓冲区

应用退出时释放不再需要的资源。

需要监测：

- PSRAM 总量
- PSRAM 空闲量
- 最大连续空闲块
- 内部 SRAM 空闲量
- DMA 可用内存

不要只看总空闲内存，还要检查最大连续内存块，避免大块图像和音频缓冲区分配失败。

## 10. 外设电源管理

### 10.1 IMU

QMI8658 采用按需启用策略。

- 不使用姿态或动作识别时，停止高频采样。
- 需要姿态数据时，按功能需求选择采样频率。
- 不需要传感器时，进入传感器低功耗或休眠模式。
- 如果后续需要抬起唤醒，可再评估低功耗运动检测方案。

### 10.2 TF 卡

- 仅在 Music Player 或 File Manager 使用时访问。
- 减少小块、频繁读取。
- 对图片、音乐等资源采用合理缓冲。
- 应用退出时关闭文件句柄。
- 不进行后台目录扫描或文件索引。

### 10.3 RTC

PCF85063 负责必要的时间保持。

除非产品后续需要 RTC 定时唤醒，否则不增加不必要的高频访问。

### 10.4 AXP2101

通过 AXP2101 获取硬件支持的电源和电池信息。

需要验证当前 BSP 驱动支持哪些能力：

- 电池电压。
- 电池电量估算。
- 充电状态。
- USB 外部供电状态。
- 电源轨控制。
- 电池充放电相关状态。

不能仅凭芯片型号推断所有电池电流和功率数据均可读取。

## 11. Power Manager 电源状态机

### 11.1 状态定义

| 状态          | 说明           |
| ----------- | ------------ |
| ACTIVE      | 前台应用正常运行     |
| IDLE        | 前台应用空闲，无活跃业务 |
| DIMMED      | 屏幕降低亮度       |
| DISPLAY_OFF | 显示面板关闭       |
| LOW_POWER   | 系统低功耗运行      |
| LIGHT_SLEEP | 系统进入轻睡眠      |
| DEEP_SLEEP  | 系统进入深度睡眠     |

第一版重点实现 ACTIVE、IDLE、DIMMED、DISPLAY_OFF 和 LOW_POWER。

LIGHT_SLEEP、DEEP_SLEEP 先预留，不作为第一阶段强制功能。

### 11.2 状态转换

```
                 用户操作
                    |
                    v
                 ACTIVE
                    |
             一段时间无操作
                    |
                    v
                 DIMMED
                    |
             继续无操作
                    |
                    v
               DISPLAY_OFF
                    |
          无前台业务和网络需求
                    |
                    v
                LOW_POWER
                    |
             触摸/系统唤醒
                    |
                    v
                 ACTIVE
```

状态转换需要考虑：

- 正在播放音频。
- 正在执行语音交互。
- 正在执行文件操作。
- 正在进行重要数据写入。
- 当前应用是否申请显示锁。
- 当前应用是否申请网络锁。

### 11.3 资源锁机制

为防止应用进入某些场景时被系统错误地熄屏或关闭网络，建议实现短时资源锁。

第一版资源锁：

| 锁            | 作用            |
| ------------ | ------------- |
| Display Lock | 暂时阻止自动熄屏      |
| Network Lock | 暂时保持网络连接      |
| Audio Lock   | 防止音频资源被其他模块释放 |

锁必须有明确的释放路径，必要时增加超时租约，避免异常退出后一直占用资源。

资源锁只用于前台业务，不用于维持后台应用。

### 11.4 自动熄屏与唤醒

- 用户触摸、按键等有效交互后重置计时器。
- 进入 DISPLAY_OFF 时执行面板休眠。
- 唤醒时恢复面板和 LVGL 状态。
- 如果设备进入 LOW_POWER，应确保唤醒源配置正确。
- 第一次触摸仅用于唤醒。

## 12. ZCode Remote 特殊电源策略

ZCode Remote 不提供后台连接保活。

### 12.1 会话与连接分离

需要区分：

**会话信息持久化：**

- 服务器配置 ID
- Session ID
- 终端标识
- 会话名称
- 上次连接时间
- 上次已知状态

**实时连接状态：**

- WebSocket
- SSH
- 远程任务连接
- 实时状态同步

第一版只持久化会话信息，不维持实时连接。

### 12.2 生命周期

进入 ZCode Remote：

1. 展示已保存的服务器配置。
2. 展示历史会话。
3. 用户手动选择会话。
4. 重新建立网络连接。
5. 向服务端同步真实会话状态。

退出 ZCode Remote：

1. 停止轮询。
2. 断开 WebSocket/SSH 等连接。
3. 保存必要的会话标识和展示信息。
4. 释放网络资源。

再次进入时：

- 不自动建立历史连接。
- 用户手动选择恢复。
- 服务端返回的实际状态覆盖本地缓存。
- 已不存在或不可恢复的会话显示相应提示。

## 13. 电池监测与设备信息

### 13.1 电池监测

Device Monitor 负责采集硬件支持的电池状态。

建议展示：

- 电池电量（如果驱动提供可靠估算）
- 电池电压
- 是否正在充电
- USB 外部供电状态
- 电池状态更新时间

第一版可以采用低频刷新，不需要持续高频读取。

### 13.2 设备运行信息

设置中的设备信息页面建议展示：

- 固件版本
- 固件构建时间
- 芯片型号
- 当前 CPU 频率
- Flash 总量
- PSRAM 总量
- PSRAM 空闲量
- 最大连续空闲块
- 内部 SRAM 空闲量
- DMA 可用内存
- 电池状态

ESP-IDF 可以通过 heap capabilities 相关 API 获取内存信息，例如：

- `heap_caps_get_total_size()`
- `heap_caps_get_free_size()`

可通过分配能力标志区分 PSRAM、内部 RAM 和 DMA 内存。

Flash 分区信息可以通过 ESP-IDF 分区 API 获取。

## 15. 第一版实施计划

### 阶段一：基础资源管理

目标：保证应用切换时资源能够正确释放。

- 建立 Power Manager。
- 建立 App Lifecycle 接口。
- 建立统一 Network Manager。
- 建立统一 Audio Manager。
- 实现应用退出清理流程。
- 确保所有应用没有后台业务轮询。
- 确保应用退出后关闭业务连接。

验收标准：

应用退出后，不再有该应用的定时网络请求、业务连接、音频采集或动画任务。

### 阶段三：网络与外设优化

- 应用进入前台立即刷新。
- 应用离开后停止定时刷新。

- 实现指数退避。
- 实现 Wi-Fi 按需关闭。
- 实现 IMU 按需启用。
- 实现 TF 卡按需访问。

验收标准：

后台无应用级主动网络请求，且应用再次进入后能够正常刷新。

### 阶段四：CPU 与内存优化

- 实现 CPU 性能等级。
- 优化 FreeRTOS 任务休眠。
- 实现动画帧率分级。

- 监控 PSRAM 和内部 SRAM。

### 阶段五：系统睡眠能力

- 验证触摸唤醒条件。
- 验证 RTC 唤醒能力。
- 评估 Light Sleep。

## 16. 功耗测试与验收

### 16.1 测试场景

必须覆盖以下场景：

| 编号  | 测试场景                     | 重点观察       |
| --- | ------------------------ | ---------- |
| T01 | 开机空闲，屏幕亮                 | 基础功耗       |
| T02 | 开机空闲，屏幕关闭                | 熄屏收益       |
| T03 | 角色 Idle 动画               | 动画功耗       |
| T04 | AI 语音交互                  | 音频和网络功耗    |
| T05 | Subscription Center 前台刷新 | 网络请求功耗     |
| T06 | Weather 前台刷新             | 网络请求功耗     |
| T07 | Komari 前台监控              | 网络和 CPU 功耗 |
| T08 | ZCode Remote 连接          | 长连接功耗      |
| T09 | ZCode Remote 退出          | 断开连接后的功耗   |
| T10 | Music Player 播放          | TF 和音频功耗   |
| T11 | 应用切换多次                   | 资源释放和内存变化  |
| T12 | Light Sleep              | 睡眠功耗       |
| T13 | Deep Sleep               | 深度睡眠功耗     |

### 16.2 测试指标

建议记录：

- 平均电流
- 峰值电流
- 电池电压
- CPU 使用情况
- PSRAM 使用情况
- Wi-Fi 状态
- 显示状态
- 音频状态
- 测试持续时间

功耗测试应尽可能在相同供电电压、相同亮度、相同网络环境下进行。

如果使用 USB 供电测量，需要确认测量位置和电源路径；USB 输入电流不一定等于电池侧电流。

### 16.3 续航估算

在获得稳定平均电流后，再估算续航。

简单估算：

`续航时间（小时）≈ 电池容量（mAh）÷ 平均电流（mA）`

该公式只适合初步估算。实际续航还会受到电池可用容量、转换效率、放电曲线、温度和电池保护阈值影响。

在电池容量、板级实际功耗和电源转换效率尚未确认前，不承诺具体续航时间。

## 17. 风险与注意事项

### 17.1 屏幕休眠

面板休眠和电源轨关闭需要根据官方 BSP 驱动实现，不能直接假设发送黑屏命令就能显著降低功耗。

### 17.2 Wi-Fi 关闭

关闭 Wi-Fi 可以减少空闲连接功耗，但重新连接会带来额外耗电和等待时间。需要测试不同策略的总能耗。

### 17.3 音频关闭

Codec、ADC、I2S 和功放之间存在硬件关联。关闭顺序应以当前音频驱动和硬件原理图为准。

### 17.4 PSRAM 与 DMA

部分外设 DMA 不能直接使用所有 PSRAM 内存区域。释放和重新分配缓存时要遵循 ESP-IDF 的内存能力约束。

### 17.5 Deep Sleep

Deep Sleep 可能导致运行状态丢失，需要重新初始化显示、网络和外设。第一版应优先保证普通熄屏和低功耗运行可靠。

### 17.6 不能直接套用芯片睡眠电流

ESP32-S3 芯片自身的典型睡眠电流不代表整块开发板的睡眠电流。AMOLED、PMU、PSRAM、触摸控制器及其他外设都可能产生额外功耗。

## 18. 最终设计决策

第一版最终采用以下策略：

1. 所有业务应用前台独占运行。
2. 所有应用均不提供后台业务服务。
3. 应用离开前台后停止刷新、断开业务连接、释放资源。
4. ZCode Remote 仅保存历史会话信息，不维持后台连接；重新进入后由用户手动恢复。
5. Subscription Center、Weather、Komari 进入前台后立即刷新，前台停留期间按配置周期刷新。
6. 屏幕采用自动熄屏和触摸唤醒。
7. 熄屏后停止 LVGL 动画解码和无意义刷新。
8. 音频设备按需开启，交互结束后及时关闭。
9. Wi-Fi 按前台业务需求开启，无网络需求时允许关闭。
10. CPU 根据当前工作负载动态调整性能。
11. IMU、TF 等外设按需启用。
12. 第一阶段不强制使用 Deep Sleep。
13. 通过实际功耗测试决定后续优化方向。

**最终目标：设备在有人操作时保证流畅体验，在没有操作和业务需求时尽可能降低功耗。**

## 附：实施提示（落地时保留）

1. **先不要急着实现 Deep Sleep。** 先把应用退出清理、屏幕真实休眠、音频关闭、网络按需连接做好，这些更容易验证，也更不容易影响系统稳定性。
2. **电源管理必须和应用生命周期一起开发。** 不要等所有应用都写完再补，否则每个应用可能形成独立的网络和外设管理逻辑。
3. **先建立功耗基线。** 板子到手后，先测亮屏空闲、熄屏空闲、Wi-Fi 开启、语音交互四种场景，再决定后续优化优先级。

后续工作：把本方案拆解为 ESP-IDF 的 `PowerManager`、`NetworkManager`、`DisplayManager`、`AudioManager` 模块接口与开发任务清单（`firmware/components/`，power_manager 已先行落地电池域）。
